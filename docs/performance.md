# 性能记录

日期：2026-10-18。机器：AMD Ryzen 7 9800X3D，Windows，CPython 3.11.9。结果为单进程实测，不代表硬件绝对极限。

每组重复 3 次，每次 200,000 个决策，取耗时中位数。固定随机选择器、随机阵容与种子；每 1,000 步或自然胜利重开，覆盖不同兵种和阶段。原始结果在 [benchmarks](benchmarks/) 中保留。

| 路径 | 决策/秒，中位数 | 测量范围 |
| --- | ---: | --- |
| 双人，同一 16 兵种实现优化前 | 45,739 | 动作生成、编码、合法性校验、执行 |
| 双人，当前状态推进 | 57,426 | 同上，约提高 26% |
| 四人，当前状态推进 | 49,900 | 同上 |
| 双人，每步生成字典观测 | 20,970 | 含完整玩家可见观测与候选 |
| 双人，每步生成紧凑数值观测 | 32,873 | 含数值缓冲区与候选，较字典路径约提高 57% |

不包含模型推理、HTTP、数据库、JSON 网络编码、逐步完整轨迹摘要或逐步不变量验证。打开这些功能会增加开销；不得把纯状态推进数值当作端到端训练吞吐。每步观测两种格式的自然胜局数均为每次 48 局；纯四人测量为每次 52 局，其余局面在测量步数段末被重置。

## 已采用的优化

- 邻接格、距离表、数值观测空棋盘模板与坐标偏移预计算。
- 不可变动作对象复用，LRU 上限 65,536，避免持续无界增长。
- 当前环境按 revision 缓存合法候选和动作编码，只在状态变化后重新生成。
- 安全入口先做合法性检查；受信任、已经选中合法候选的模拟执行不重复生成整张动作表。
- 随机袋均匀索引抽取并交换删除，避免列表中段删除的搬移。
- 分支克隆只复制需要隔离的可变字段和随机状态，替代通用深复制；跳过不必要的重新播种。
- 数值观测使用固定模板与稀疏填入有效单位/兵种，避免每步构建大量字符串字典。
- 展示文本、观测、日志摘要和回放记录按需生成；纯模拟不访问存档服务。
- 网页签名动作与展示候选按 revision 缓存；网页动作在 SQLite 提交成功后更新内存。

曾尝试对 `encode_action(Action)` 添加通用 LRU，但动作哈希开销使实测变慢，已撤回。保留有实际收益的优化。

## 复现

```powershell
python -m backend.benchmark --steps 200000 --repeats 3 --players 2
python -m backend.benchmark --steps 200000 --repeats 3 --players 4
python -m backend.benchmark --steps 200000 --repeats 3 --observation dict
python -m backend.benchmark --steps 200000 --repeats 3 --observation packed
```

`components` 另外测量一组中间局面的动作生成、克隆、观测与内部执行平均耗时；独立调用的观测方便函数也会生成合法候选，不能把它和缓存命中的观测调用混为一谈。桌面其他任务、阵容、局面复杂度和解释器版本都会影响结果。

优化前基线取自本次完成 16 兵种后、引入动作复用及克隆优化前的版本，应用了相同的两步折返规则；它不是原来只有 8 兵种样机的速度。基线采集时项目尚未初始化 Git，故将该基线的原始测量保存为 JSON，不伪造版本提交号。

## 进一步扩展的依据

先测实际模型推理、采样进程、观测传输和学习器利用率，再决定优化位置。多个独立采样进程可使用不同种子；当前未做多核线性扩展或 GPU 吞吐声明。

若实际需要百万级单进程模拟，可在现有语义动作、规则场景与回放摘要基础上实现原生内核，并做相同种子/动作序列的差分验证。当前交付的是已经测量和验证的 Python 底座，不能称为已达到极限的原生训练引擎。
