# 后续训练方案：LLM 冷启动与自博弈

状态：设计记录，尚未实现模型或调用 LLM 生成对弈数据。用户明确要求先完成基础版游戏底座和 API。

## 用户提出的路线

先让 LLM 下几十局，留下冷启动对弈数据。在对弈及复盘中，让 LLM 提出奖励、模型架构、输入输出设计的候选，并分析如何更充分地利用每条数据。进一步探索用 LLM 分析结果进行数据增强、构造新局面与反事实对弈，降低冷启动难度。

这条路线保留为主线；“几十局足够训练出强模型”目前没有证据，应把最初几十局视为验证数据管线、覆盖基础决策和发现规则问题的起点。

## 从觉悟工作中借鉴什么

- [JueWu-SL](https://arxiv.org/abs/2011.12582) 展示了监督学习整合宏观策略与微操的可能性。这里可借鉴“先从示范建立可用策略”的思路；LLM 样本并不等于高质量人类专家示范。
- [Towards Playing Full MOBA Games with Deep Reinforcement Learning](https://arxiv.org/abs/2011.12692) 使用课程自博弈、策略蒸馏、离策略适配、多头价值估计等技术处理大英雄池。这里拟借鉴课程难度、阵容泛化和自博弈评估，不能直接照搬 MOBA 的奖励或网络规模。
- [Honor of Kings Arena](https://arxiv.org/abs/2209.08483) 提供观测、动作和奖励接口，并强调不同可控角色与对手带来的泛化问题。战争之匣也应按兵种组合留出评估集。
- [Hokoff](https://arxiv.org/abs/2408.10556) 讨论真实对局离线数据及分层动作挑战。可将离线学习作为候选，但需要先检查本项目数据量、质量和分布覆盖。

下面均是针对本项目提出的实验设计，不能当作上述论文已经验证过的结论。

## 第一批对局

建议先采集 32–64 局，按预算调整，不先承诺样本数足够。

1. 先做双人推荐阵容和单能力场景，排查协议误解。
2. 加入随机阵容、历史阵容、颜色互换和成对种子，避免只学会一种兵种组合。
3. 少量选兵局单独标记；四人局后置，避免最初把协作与基础对战混在一起。
4. LLM 只获得自己席位观测、公共历史、规则说明和合法候选；必须从候选编码选择。
5. 每步记录简短的策略说明、主要备选、置信度及教师版本。结构化说明是分析标签，不把冗长自然语言推理当作网络必须模仿的目标。
6. 所有动作经过引擎执行。结束后校验完整回放，记录自然胜负或采样截断；失败、协议重试、规则误解单独标记。

规则、观测和动作版本固定后再开始正式采集；修复影响语义的错误时重放旧样本，必要时作废而不是悄悄改标签。

## 数据分层与质量

每条样本至少关联：`episode_id`、规则/观测/动作版本、阵容、席位/队伍、局面版本、实际可见输入、合法候选、所选动作、即时/终局标签、采样是否结束及原因、教师与提示词版本、简短分析、来源和父样本 ID。

受信任的完整回放保存隐藏状态；策略样本只保存玩家可见信息。赛后 LLM 可以分析全局真相，但应把这种分析标为 privileged annotation，不能回填为当时策略知道的事实。相同可见局面在不同隐藏状态下，最优决策可能不同。

按**原始对局与增强家族**分组划分训练/验证/测试。不能随机按相邻决策行划分，也不能把同局颜色互换的版本分到测试集。原始示范、人工修订、LLM 伪标签、引擎验证分支分层计数，避免增强后把数据量误报为独立真实对局数。

## 输入输出与架构候选

输入候选：棋盘单位与增援数、据点归属、双方阵容/供应/公开弃币/移除区、自己手币和袋币计数、隐藏区公开数量、阶段和结算栈、先手/行动席位/队伍、公共历史。相对己方规范化可以做，但四人所有者和队伍不能混为一谈。

输出优先比较“给当前合法候选评分”的策略头：候选中包括动作类别、支付币、起点、终点、指挥者或攻击目标、招募类型等。直接采样候选避免非法动作；padding mask 与规则合法性分开。

至少比较三种规模：

- 小型 MLP + 候选动作嵌入，作为速度和数据效率基线。
- 六角棋盘图网络或共享格子编码 + 手牌/供应集合编码 + GRU，利用空间结构并保留公共历史记忆。
- 小型 Transformer 编码棋盘实体和公共事件，再对候选交叉评分，检验额外容量是否值得。

价值头预测己方队伍胜率。辅助头可尝试后续据点变化、公开战损、袋循环阶段或 LLM 战术类别；逐项消融。不要一开始把“大网络”“更多标签”与“更高数据利用率”画等号。

## 奖励候选

底座仅实现终局队伍 `+1/-1`，其他时间零；截断不是和棋。后续将以下候选作为实验，不固化为游戏规则：

- 据点差、可达控制点、主动权等有界势函数 `Phi`；采用 `r' = r + gamma*Phi(s_next) - Phi(s)`，并正确处理终局势与截断，减少随意稠密奖励改变目标的风险。
- 战损和招募只作分析信号或辅助任务，避免模型为杀兵、刷招募、来回夺点而放弃胜利。
- LLM 给出的“好手/坏手”是待验证偏好标签。用分支模拟、固定对手与留出局面评估验证，不能直接把文字评价当作真实回报。
- 特殊子阶段的折扣和记账要统一：一次普通用币产生多个决策，不应凭空多发奖励；跨席位结算按队伍和实际控制者处理。

## 增强与制造数据

先从可证明保持规则的变化开始，再探索更强增强：

1. 半周旋转棋盘并同步交换阵营、单位所有者、出手顺序、动作和奖励；先验证地图与整条轨迹一致。不要套用任意六角旋转或镜像。
2. LLM 提出关键局面的备选动作，从受信任快照生成分支，通过引擎检查合法性与守恒，再用公平对手完成后续模拟。标记为反事实分支，保留父节点与生成方式。
3. 让 LLM 按战术概念提出场景，例如“是否争先手”“增援后的骑士门槛”“牧师连动”。场景必须由合法前缀到达，或明确标注为人工场景，不能混充完整真实对局。
4. 对相同玩家可见信息，采样符合其知识的多种隐藏状态，检查建议是否过度依赖某个真实对手手牌。不要通过修改观测中的未知字段直接伪造结论。
5. 选择信息量高、教师分歧大、学生不确定的分支增加标注，限制相似样本重复权重。

LLM 负责提出、解释、筛选；规则真值、动作合法性和轨迹一致性由引擎负责。增强不能凭空制造可靠胜负标签。

## 训练与评估顺序

待底座验收后：行为克隆基线 → 质量分层与辅助任务消融 → 小规模自博弈 → 固定旧版本/随机与脚本基线混合的对手池 → 更广阵容课程 → 蒸馏与吞吐优化。离线 RL 是否有收益另做对照。

以留出的阵容、成对种子、颜色互换对局与固定对手胜率作为主要评估，报告样本数和不确定性。单独统计非法/过期请求率、自然完局率、截断率和吞吐。使用真实隐状态或未来随机数的搜索结果必须单列，不能并入公平胜率。

模型和数据增强代码暂缓；先确保所有采集结果能被版本化、重放和检查。
